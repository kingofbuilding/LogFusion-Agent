## 1. 调查与工具层

### 1.1 工具参数范围没有写进 schema，模型只能试错

- **现象**：LLM 组 100% 的运行至少出现一次工具调用失败；2 例连续 3 次失败后被 `tool_error_limit` 终止，调查没有任何结论。
- **根因**：`TOOL_SCHEMAS` 只声明 `type: integer`，`max_groups ≤ 10` 这类约束只写在 `InvestigationTools.call` 里。模型看不到边界，只能猜。
- **定位**：把单次运行的 trace 打出来，看到连续的
  `aggregate_events({"window_minutes": 60, "min_failures": 3, "max_groups": 20})` → `ValueError`；
  第二次改成 `min_failures: 2` 但仍保留 `max_groups: 20` → 再错；第三次去掉该参数才成功。
- **处置**：schema 增加 `minimum`/`maximum` 与范围描述；越界时抛 `ToolArgumentError`，把可读原因和 `retry_guidance` 回灌给规划器，而不是只回一个 `ValueError` 类型名。
- **效果**：工具报错率从 1.00 降到 0.24；完成率从 0.43 升到 0.81（该对比同时放宽了步数预算，见 1.2）。
- **状态**：已修复（该修复由并行会话落地，本记录仅做复盘与验证）。
- **证据**：`benchmarks/results/eval_llm_20261021T164242Z.json`（修复前）、`benchmarks/results/schema16/eval_llm_20261021T233038Z.json`（修复后）。

### 1.2 12 步预算对 50 行以上的日志偏紧

- **现象**：修复前 21 次运行里有 8 次停在 `max_steps`，其中 2 次因此证据召回为 0。
- **根因**：阶段 0 的基线用的是 15 条日志的 demo，12 步够用；评测用例有 49–72 条噪声，检索与上下文确认的成本更高。
- **处置**：修复后的 C/D 组统一用 16 步。副作用是 C0→C1 的对比变成“schema + 预算”两个变量，报告已注明。
- **状态**：已调整，但引入对比混杂（见 5.2）。

### 1.3 token 软预算在调用之间检查，会超

- **现象**：`ssh-033` 触发 `token_budget` 时已累计 104331 tokens，超出 100000 的上限 4.3%。
- **根因**：预算只在每次模型返回后、下一次调用前检查；在途请求无法中断。
- **处置**：不改代码，因为这是有意的软预算。把它写进 README 与评测报告，并把该次运行按“未完成”统计，不伪装成成功。
- **状态**：已知边界，保留。

### 1.4 `temperature=0` 不是确定性的

- **现象**：同一用例 `ssh-016` 首次评测停在 `tool_error_limit`，复跑却正常完成；`ssh-010` 首次是 `repeated_tool_call`，复跑变成 `max_steps`。
- **根因**：服务端推理与并发调度带来非确定性，客户端只能固定采样温度。
- **处置**：报告明确“单次运行只能当样本”，评测建议 3 次重复取均值。
- **状态**：未解决，属外部服务特性。

## 2. 评测框架

### 2.1 标注规则与证据层同源，结论正确率有天花板

- **现象**：规则剧本组 42/42 全对，看起来“完美”。
- **根因**：用例的期望结论正是按 Agent 的 5 次/5 分钟/15 分钟规则构造的，判分器与实现共享同一套定义。
- **影响**：verdict 正确率只能衡量管线一致性，不能证明检测能力；A 组也因此拿到 1.00。
- **处置**：在报告里把它列为首要限制，并把有效指标改为证据召回、证据精度、误关联、成本与完成率。
- **状态**：方法论限制，无法靠改代码消除，只能披露。

### 2.2 只有召回、没有精度，窗口级证据会被误读

- **现象**：A 组证据召回 1.00、结论正确率 1.00，看起来优于 Agent；实际每次要看约 50 条日志才能覆盖 7–8 条标注事件。
- **根因**：初版指标只统计“标注事件被查到的比例”，没有惩罚“查了太多无关事件”。
- **处置**：新增 `evidence_precision` = 标注事件 ∩ 已查证据 / 已查证据。A 组 0.14、B 组 0.26、D 组 0.18，粗粒度问题立刻显形。
- **状态**：已修复。

### 2.3 用例标签必须自检，否则可能“不可达”

- **问题**：手工拼日志时，很容易写出“期望关联成功登录，但失败簇根本没达到 5 次阈值”的用例，评测器会把实现判错，而实际是标签错。
- **处置**：生成器写盘后重新载入，用与 Agent 完全相同的 `failure_clusters` 反解失败簇，必须与注入的簇一一对应，否则生成直接失败；`tests/test_eval_harness.py` 还校验每个标签 ID 都真实存在于该用例。
- **状态**：已实现。

### 2.4 用例长度与检测器窗口要求冲突

- **现象**：`ssh-033`、`ssh-036` 只有 49 条日志，检测器要求 `temporal_sequence_length=50` 才能出分，A 组返回 `detector_unavailable`，完成率降到 0.95。
- **根因**：生成器的噪声条数是 45–60 的随机值，没有为下游 50 条窗口留下限。
- **处置**：本轮不改用例（改了会重排所有行号、让已有结果失效），在报告中披露这 2 条；下轮把噪声下限提到 55。
- **状态**：已知，待下轮修。

### 2.5 冒烟运行污染结果目录

- **现象**：`--limit 3` 的试跑把 `eval_upstream_*.json` 写进了正式结果目录，报告引用时容易混。
- **处置**：删除试跑产物，只保留全量运行；后续试跑改用临时 `--out` 目录。
- **状态**：已清理。

### 2.6 结果字段契约漂移，测试直接 KeyError

- **现象**：给 `score_case` 增删字段后，`test_summary_skips_undefined_metrics` 因缺少 `evidence_count` 报 KeyError。
- **根因**：测试用“手工构造的最小 row”喂 `summarize`，与真实结果字段没有共享定义。
- **处置**：`summarize` 对可选字段用 `.get(...)` 兜底，测试 fixture 补齐为完整 schema。
- **状态**：已修复。

## 3. 上游集成

### 3.1 迁移的向量索引在哈希嵌入下不可用

- **现象**：`retrieve_cases` 走 `upstream_vector_rag` 时永远返回空列表，D 组的 RAG 分支等于没有。
- **定位**：直接算查询向量与 67 条案例的余弦相似度，最高 0.1431、中位数 0.0；而配置要求 `raw_score_threshold: 0.65` 且 `similarity_threshold: 0.7`。
- **根因**：前身工程与本仓库都设了 `force_hash_fallback: true`，语义向量是 256 维哈希桶而非 MiniLM 句向量；哈希嵌入对短查询几乎没有区分度。索引本身没坏，是嵌入方式的问题。
- **处置**：不降低阈值伪装“检索成功”，保留严格阈值并在报告、README、UPSTREAM.md 中写明 D 组差异只来自检测器。
- **后续**：安装 sentence-transformers、用 MiniLM 重建索引；但融合模型是在哈希特征上训练的，换嵌入方式需要重训或至少重标定（见 3.5）。
- **状态**：未解决。

### 3.2 窗口分数只映射到末行，标注事件永远不可见

- **现象**：A 组第一版在所有用例上证据召回都是 0。
- **定位**：把证据的文件行号打出来，发现只落在最后 17 行（66 条日志取 50 条窗口，只有 17 个窗口末行），而标注的失败簇在第 35–47 行。
- **根因**：上游按序列窗口打分，适配层却把分数当作“末行这一条事件”的分数；窗口内部的任何事件都无法被选中。
- **处置**：适配器额外返回 `windows: [{start_event_id, end_event_id}]`，A 组按窗口跨度展开事件作为证据；同时新增证据精度暴露粒度代价。
- **状态**：已修复。

### 3.3 检测器输出体积过大，把预算烧光

- **现象**：D 组 9/21 撞 `token_budget`（C1 只有 2 次），平均 token 从 73k 升到 89k，完成率从 0.81 降到 0.52，结论正确率没有提升。
- **根因**：`detect_anomalies` 一次返回 30 条分数（含三个视图分）加 30 个窗口跨度，形成很大的 tool observation；规划器每一轮都要重放整段对话，成本被放大。
- **处置**（已实施）：
  1. `detect_anomalies(top_windows=5)` 只返回 top-N 个窗口，每个窗口只带跨度、风险分、主要贡献视图与三视图分数，不再返回逐条原始分数；实测单次观察从约 10 KB 降到 876 字符。
  2. 参数 `top_windows` 在 schema 中声明 `1..10`，沿用 1.1 的教训。
  3. 截断披露：返回 `total_windows`、`returned_windows`、`truncated`，并在 `notice` 中说明窗口内事件需用 `search_logs` / `get_event_context` 查询。
  4. 通用兜底：`call()` 对所有工具结果做 6000 字符上限（`_fit_observation`），超限时裁剪首个大列表并写 `observation_truncated` / `observation_note`。以后新增 Web 场景工具也受同一约束。
  5. 只把窗口锚点事件写入证据，避免一次调用塞入几十条事件。
- **验证**：`tests/test_observation_limits.py` 覆盖窗口裁剪、参数越界、未知事件 ID、通用上限与“小结果不被改动”。
- **状态**：已修复。

### 3.4 Bi-LSTM 检查点必须回退 `weights_only=False`

- **现象**：`torch.load(..., weights_only=True)` 报 `Unsupported global: numpy.core.multiarray.scalar`，加载失败；代码回退到 `weights_only=False` 后才成功，并打印安全警告。
- **影响**：只影响信任边界——从不可信来源下载的检查点可能执行任意代码。
- **处置**：保留回退（上游行为），在 UPSTREAM.md 注明“仅加载本地可信来源的权重”。
- **状态**：已记录，不修。

### 3.5 检测器与 RAG 必须成套迁移

- **问题**：融合模型、语义视图与案例索引是在同一套哈希嵌入配置下产出的。单独替换其中一个（例如只把索引换成 MiniLM），会造成训练/推理特征不一致，分数漂移且没有报错。
- **处置**：写进 UPSTREAM.md 与评测报告，作为“重建索引前必须先决定是否重训”的前置条件。
- **状态**：文档约束。

### 3.6 两个仓库的案例文件同名不同内容

- **现象**：`data/rag/attack_cases.jsonl` 在两个仓库里都是 67 条、`case_id` 相同，但内容不同。
- **影响**：如果只复制 `.jsonl` 而不复制索引，或反之，可能出现“案例文本与向量不匹配”，且没有任何断言会发现。
- **缓解**：迁移的 `.npz` 自带 `payloads`，加载时以索引内 payload 为准，因此本次只复制索引是自洽的；但这是一个隐性契约，值得加校验。
- **状态**：本次自洽，建议后续加一致性检查。

## 4. 环境与协作

### 4.1 Windows 控制台中文乱码

- **现象**：`Get-Content` 与 `python` 输出中文都显示为 `����` 或 `璋冩煡`。
- **根因**：控制台代码页与 Python stdout 编码不一致；文件本身是 UTF-8，没有坏。
- **处置**：运行时设 `PYTHONIOENCODING=utf-8`，脚本内 `sys.stdout.reconfigure(encoding="utf-8")`；检查文件内容改用 `read` 工具而不是通道输出。
- **状态**：已规避。

### 4.2 PowerShell 不支持 `<<` heredoc

- **现象**：`python - <<'PY' ... PY` 直接报解析错误。
- **处置**：改用 `$code = @'...'@ ; $code | python -`。
- **状态**：已规避。

### 4.3 成功的命令显示 exit 1

- **现象**：Python 往 stderr 打日志，经 `2>&1 | Select-Object` 后被 PowerShell 包装成 `NativeCommandError`，命令实际成功却报 `[exit code: 1]`。
- **影响**：如果按退出码判断成败，会把正常评测误判为失败。
- **处置**：判断成败以输出内容与结果文件为准；评测脚本内部 `logging.disable(INFO)` 降低 stderr 噪声。
- **状态**：已识别。

### 4.4 文件写入 EIO（Win32 1175）

- **现象**：`edit` 工具替换文件时报 `ReplaceFileW EIO (Win32 1175): ...`，重试同一操作就成功。
- **根因**：写入采用“写临时文件 + 替换”，目标文件被杀毒/索引器短暂占用时替换失败。
- **处置**：失败后重读文件再重试；大量改动时直接整体重写，避免多次小替换。
- **状态**：已规避。

### 4.5 并行会话共用同一工作区

- **现象**：`run_eval.py` 出现自己没写过的字段名（`judgment_decoy_citations`）、预算从 12 被改成 16、`tests/test_eval_harness.py` 在我读取后被改动；随后仓库又出现 `benchmarks/run_injection.py`、`benchmarks/results/injection/`、`tests/test_tool_constraints.py` 与 `schema16/` 结果。
- **根因**：另一个会话/进程在同一目录并行开发（工具 schema 修复、注入测试），与本会话的改动交叉。
- **影响**：一度出现编辑失败、字段契约不一致、以及 C 组与 D 组预算不可比。
- **处置**：每次编辑前重新读取；冲突文件整体重写；D 组预算对齐到 16 步；报告中明确 C1 数据来自并行会话的 `schema16` 运行。
- **状态**：部分缓解，仍需人工协调。

### 4.6 测试对字典字段硬依赖

- 见 2.6，同源问题：`summarize` 的输入契约没有类型/字段定义，只能靠约定。后续可考虑用 `TypedDict` 或 dataclass 固定结果行结构。

## 5. 未解决清单

### 5.1 语义检索不可用（3.1）

需要：安装 sentence-transformers、下载 MiniLM、重建 67 条案例索引；同时决定是否重训融合模型，否则语义视图特征漂移。

### 5.2 C0→C1 变量混杂（1.1 + 1.2）

同一轮里改了 schema 与步数预算，无法拆分贡献。需要补两组对照：12 步 + 新 schema、16 步 + 旧 schema。

### 5.3 检测器上下文膨胀（3.3）

需要改工具返回：分页、只给窗口首尾、或按实体聚合；目标是 D 组完成率回到 0.8 以上且 token 不超过 C 组的 1.2 倍。

### 5.4 用例长度下限（2.4）

噪声下限提到 55 条，保证所有用例都能喂给 50 条窗口的检测器；需要接受行号与事件 ID 全部变化，旧结果重跑。

### 5.5 重复次数不足

C/D 目前各只跑 1 次、每类 3 条，无法给方差。计划 42 条 × 3 次。

### 5.6 阶段 4 的工程缺口（未开始）

进程重启后的 checkpoint/恢复、UI 取消按钮、工具失败重试与指数退避。

## 6. 经验

1. **约束要写进模型能看见的地方**：代码里的参数校验不等于模型知道边界；schema 不写范围，就等于让模型用 token 买试错机会。
2. **指标要成对**：只报召回，粗粒度方案必然“赢”；精度让代价显形。
3. **标签要能自检**：写盘后用同一套实现反解，能挡住绝大多数“标注错、怪实现”的误判。
4. **窗口级模型不能直接当事件级证据**：聚合粒度是接口契约的一部分，必须在适配层显式建模。
5. **非确定性要当成常态**：单次结果只能当样本，对比实验必须固定预算、重复运行、披露停止原因。
6. **把失败原因留在结果里**：`stop_reason` 与工具错误类型比“成功率”更能解释问题，也是后续优化的入口。
